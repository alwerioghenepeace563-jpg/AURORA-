# AURORA Multi-step Task Orchestration

## Purpose

The task orchestrator is an internal service shared by AURORA chat, Pulse and voice. It does not add a dedicated page. A surface can create a structured plan, show its preview, and run it only after an explicit user confirmation.

## Runtime API

The shared runtime exposes:

- `auroraRuntime.createTaskPlan({ title, summary?, steps })`
- `auroraRuntime.runTaskPlan(planOrId, { confirmed: true })`
- `auroraRuntime.tasks.getPlan(id)`
- `auroraRuntime.tasks.listPlans()`
- `auroraRuntime.tasks.getRun(id)`
- `auroraRuntime.tasks.subscribe(listener)`

Each step contains a stable `id`, a registered `capabilityId`, a typed `input` object and optional `dependsOn` IDs. Dependencies must point to earlier steps. Plans are limited to eight steps in this first version.

## Execution contract

1. Creating a plan validates every capability against the live Action Engine registry.
2. Calling `runTaskPlan` without `confirmed: true` returns a preview and executes nothing.
3. Confirmed plans execute sequentially, never in parallel.
4. Every step is dispatched through the existing Action Engine. Availability checks, input validation, idempotency and capability-level approval requirements are preserved.
5. If a step is rejected, unavailable or fails, the plan stops. Later dependent steps do not run.
6. Repeated execution of the same plan ID returns its existing run result instead of repeating device actions.
7. Task lifecycle events are available to all surfaces through the task subscription API.

## Approval and safety

The orchestrator does not weaken the selected approval-first autonomy model. Medium-, high- and critical-risk capabilities remain subject to the Action Engine's approval broker. A plan-level confirmation is an additional checkpoint, not a replacement for per-action approval.

AURORA must not interpret model-generated text as a capability ID or permission. Plans can reference only capabilities already registered by trusted built-in adapters or explicitly installed extensions. The current implementation does not automatically execute plans generated by an LLM; a future planner must validate and preview its output before asking the user to confirm.

## Current boundaries

- Sequential execution only; no background execution or parallel fan-out.
- No automatic rollback. A failed plan reports completed steps and the step where it stopped.
- Task plans and run receipts are in-memory for this runtime session. Durable task history and cross-device synchronization are a separate future layer.
- The initial maximum is eight steps to bound execution time and approval complexity.
